Common pitfalls:
- `[fields]`/`.group_by`/`.sort`/`.dedupe`/row `.filter` use `rows:` fields only — not `inputs:`/`opt:` filter keys.
- `e#{…}` filters at HTTP; `binding.filter{…}` filters materialized rows. Prefer `label = e#` then filter; bare `e#.filter{…}` list-alls first. Search-only entities (no list query): scoped `e#{p#=…}` and/or `e#~"text"` — no `e#{}` list-all.
- Group/agg: `group_by(p_key).aggregate(n=count)`; bare `group_by(p_key)` ≡ `group_by(p_key, count=count)`; multi-key sugar `group_by(k1, k2, n=count)`.
- `=>` only for derive `{ k: _.field }` or `for_each`/write effects (`source => e#.m#(…)`) — not relation reads (use `child = source.r#`). A provably-singleton source (`e#(value)`) `=>` runs the effect **once**.
- Federated **write** discipline: end in a **single** created-row return — not `read_a, read_b` parallel roots; budget **one read per catalog** (avoid `.r#` fanout unless you need N rows); discover anchors live — never hardcode workspace ids.
- Transient `session materialization changed during concurrent execute` is retryable — re-issue the same `plasm_run` once.
