# Catalogue breadth: useful development signal, with a visible cost

The unchanged scheduling candidate meets the preregistered criteria on all 58 frozen variants. The first attempt was invalid before matrix measurement; r2 changes only the new abstract proof setup, adding three matching reads. It does not change the scheduling algorithm or inherited fixtures and labels.

All six prior starvation gates recover. Trajectory availability rises from 12/18 to 18/18; requests to completion or horizon fall from 118 to 26 (78%). Resource breadth remains 32/32, with requests falling from 39 to 36. The eight ordinary controls remain one search each. Across the matrix, requests fall from 165 to 70 (58%); cumulative admitted packet bytes fall by 1,448,085. These are scripted native discovery searches with fixture judgment, not measured provider tokens or agent runtime.

Four resource-breadth variants regress from one search to two: concentrated and distributed independent outcomes at 100 distractors, under both repeated and rotating request schedules. These meet the predeclared one-additional-search allowance, but must remain visible. Aggregate endpoint declaration bytes increase by 868, entirely in the trajectory cohort. This is not an estimate of transmitted context tokens.

All 137 active matcher checks pass. All three frozen cohort runners pass, including their reverse-insertion comparisons. The original production files are restored byte-for-byte. No model calls, effects, dependencies or AppWorld runs were introduced.

The mechanical lesson is that catalogue concentration can consume admission space before useful candidates reach judgment. Giving other catalogues an admission opportunity addresses that failure without changing semantic relevance judgments. It does not establish catalogue boundaries as an ideal fairness unit: splitting a catalogue changes its share, and irrelevant catalogues can delay several useful operations concentrated in one catalogue.

Next, freeze fresh controls for catalogue splitting/merging, many irrelevant catalogues, multiple useful operations within one catalogue, and within-catalogue distractor growth. Compare the same candidate against baseline without tuning it. Measure complete-path availability and request/byte/teaching cost separately. Only then decide whether to integrate this scheduling rule. Subsequent caller-progress and terminal-completion checks remain necessary; discovery coverage alone does not prove whole-agent success.

These are reused development fixtures, not a holdout or a causal claim about AppWorld performance.
