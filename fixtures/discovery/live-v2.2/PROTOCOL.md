# Native discovery live gate v2

Frozen development controls authored 29 October 2026, not a blind holdout. No AppWorld execution. Production rubric, model alias and 16,000-byte per-packet limit unchanged. One logical judgment per search; native bounded transient retries <=3 attempts/30 seconds/48,000 admitted bytes. Four searches per case, two fresh-session repeats in opposite case order: <=64 logical requests and <=192 actual attempts. No extra retries or tuning after results.

Eight structural controls: observation; exact source/preparation/consumer chain; two valid suppliers; declared cross-catalogue required acquisition; independent observations; conditional export/preview; opaque effect with unknown readiness; changed discovery need with monotonic exposure. Contracts use named concrete outputs, never “produce the requested result.” Invoice-number reading is a strict negative because its defined output serves accounting, with no declared connection to the requested domains. No positive label encodes execution permission.

Fixture labels never enter live selection or provider evidence. Oracle mode injects labels only after packet admission. Live mode calls the production transport and decoder and updates exposure/visits from actual responses. Revision switches to its second phase at search three; existing declarations remain exposed. Score only newly judged operations against that phase, never penalize previously retained declarations for remaining available.

Freeze cases, label rationales, protocol, generator and schema bytes before oracle measurement. Each useful/opaque target's standalone native packet must fit <=16,000 bytes in oracle mode. The oracle run must complete each expected path and retain each useful/opaque capability by search four (revision phase one by search two). If feasibility fails, stop without live calls or fixture tuning. Hash native sources and runner separately before launch; harness-only repairs may occur with a documented prelaunch record and refreshed source manifest, without changing frozen fixtures.

Before live execution run matcher boundary tests (authorization, closure, retries, malformed responses and oversized safe deferral). These are integrity controls, not recall cases. There is no API execution backend: mappings point at loopback port 9 and are never invoked.

Live pass: all feasible expected paths and useful/opaque targets retained within the fixed phase horizon in both repeats; no new useful/opaque judgment rejection; no strict-negative admission; no unrecovered fault or integrity violation. Opaque unknown contribution must be retained; exact uncertain choice reported separately. Both valid suppliers are useful; separately report each path, not only whether one supplier works. Report failures without changing thresholds, horizon, labels or prompts.

Save request bytes/hash, question bindings, raw provider records, native receipts, exposed capabilities and decisions after each turn. Attribute missing targets to not-indexed/unauthorized, retrieval/frontier, budget deferral or model rejection from native receipts. Measure search 1/2/4, total requests, actual-attempt input/output/cache/cost, call wall latency and whole-search latency. Missing usage fields are unavailable; do not doublecount native receipts and provider records. Existing baseline timings use fixture judgments and are not a live-model speed comparison.

The executable runner uses exclusive launch markers and new output paths. Failure ends the gate; no AppWorld run or additional arms follow automatically. A pass supports considering a limited end-to-end smoke, not a full-suite success claim.
