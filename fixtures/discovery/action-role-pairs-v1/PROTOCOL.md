# Requested versus excluded action: representation diagnostic

Question: does lexical retrieval distinguish which action is requested when a pair of self-contained requests reverses requested and prohibited roles while retaining the same normalized word set?

No production intervention. Four fresh abstract action pairs, two request orientations, zero/100 historical-record distractors: 16 variants (eight paired conditions). Authored contracts, catalogue layout, distinct operation identities and budgets are identical within each pair. Only request roles and evaluation labels differ. Original request and full contracts remain available to judgment. No query rewriting, model calls, dependencies, effects or AppWorld evaluation.

Baseline policy,16,000 bytes,one fixture judgment/search,24-search horizon,four-search availability gate. Native retrieval, allocation, frontier and teaching; forward/reverse insertion checks. Oracle fixture judgment is intentionally given different labels for the opposite requests, allowing us to distinguish retrieval information loss from a judgment failure. Labels never enter ranking or allocation. Exposing an excluded operation is not authorization to execute it; do not call retrieval of both actions itself unsafe.

Predeclared diagnostic: the initial rankings/scores should be identical because the query is represented as a normalized word set. Record initial admitted targets, desired-target ranks, first judgment/retention and completion, cumulative request/bytes. Report whether the complete requested set arrives despite the collision. Do not infer all real-world failures from this constructed counterexample. Same ranking alone does not imply system failure if both candidates fit and judgment can select the right one.

Freeze fixtures, labels, source and analysis before execution. Stop on harness faults; report ordinary availability failures. One baseline measurement, no candidate tuning or follow-on arm. This is development diagnosis, not holdout performance or a solver improvement.
